# Curation Assessment — Plan_atlas-production

## Purpose

This document records the curation decisions, evidence basis, and assessment results for extracting and organizing the ATLAS production TODO planning content into `docs/08-planning/Plans_/Plan_atlas-production/`.

## Decision: Use the Full Package as Sole Source

### Evidence Basis

Two ZIP packages were assessed:

1. **`ATLAS_Production_TODO_Package.zip`** — The predecessor package (108 tasks, 36 PART1 packs, 27 epics E1–E27)
2. **`ATLAS_Full_Production_TODO_Package.zip`** — The current package (126 tasks, 42 PART1 packs, 30 epics E1–E30)

Tools in both packages were verified identical via `diff`:
- `canonical-registry.schema.json`
- `generate_todo_system.py`
- `todo_system_lib.py`
- `validate_todo_system.py`

All 36 PART1 files exist in both packages, but the Full package versions have updated authority references (adding `ATLAS_Production_TODO_Package.zip` and `ATLAS_Assessment_Package.zip` as recognized authorities; referencing predecessor sha256 `ca960729b67579b1b08fdedea786feb4594d0649353521c9dbcaf0f2fdb2d09f`).

### Decision

**The Full package is the authoritative superset.** The Production package is already preserved within it at `source_authority/predecessor_todo_package/`. Only the Full package was extracted into this plan directory. The Production package's content is accessible but not duplicated.

## Curation Choices Applied

### 1. File Organization
The Full package's internal directory structure was preserved with one curation normalization: the package's top-level `Plan_atlas-production/` subdirectory (containing Plan-MASTER, registry, manifest, v1.2, v2.1, PART1) was **flattened to the plan root** so the plan directory directly contains these files rather than nesting them under a redundant `Plan_atlas-production/Plan_atlas-production/` path. This matches the convention used by the existing `Plan_atlas-pipeline-engine/` plan directory.

The verification register files (originally at the package root as `ATLAS_Full_*`) were placed under `registers/` for clarity. The `tools/` directory from the package is preserved as-is, though it may generate a `__pycache__/` subdirectory when run — that is a Python bytecode artifact and should be treated as disposable.

Structure:
- `README.md`, `PART1_HEADER.md` at plan root
- `Plan-MASTER_atlas-production.md` — program objective, architecture, authorities, epic index
- `TODO_atlas-production-registry.json` — canonical 126-task registry (1.7MB, the sole editable authority)
- `TODO_atlas-production-manifest.json` — package manifest
- `TODO-MASTER_atlas-production-v2.1/` — detailed implementation-grade task specs
- `TODO_atlas-production-v1.2/` — compact plan + machine-readable index
- `TODO_atlas-production-PART1/` — 42 exact three-task execution packs
- `source_authority/` — 11 architecture/authority documents + `predecessor_todo_package/`
- `registers/` — 27 verification register files (CSVs, MDs, XLSX, JSON)
- `tools/` — 4 deterministic generation/validation files
- `CURATION_ASSESSMENT.md` — this document

### 2. Canonical Authority
Per the README: **`TODO_atlas-production-registry.json` is the sole editable task authority**. All other files (Plan-MASTER, v1.2, v2.1, manifest, 42 PART1 packs) are deterministic projections. The generator/validator tools enable reproducible regeneration.

### 3. Task Structure Quality
PART1 files reviewed (spot-checked PART1-1 through PART1-3, plus PART1-37–42 for the new epics). Each task follows a consistent high-quality template:

```
* [ ] TODO N: <actionable title>
  1.2 source task(s): `T<epic>.<task>`
  Priority: `P0|P1|P2|P3`
  Estimated effort: `<N hours>`
  Dependencies: `<backward only>`
  Evidence basis: `ATTACHED-SNAPSHOT`
  Repository scope: `<components with reuse/migrate/create>`
  Required authorities: `<all cited authorities>`
  Purpose / Why this exists
  Where this applies
  Repository and authority evidence
  Current-state assessment and gap analysis
  Design and integration strategy
  Implementation requirements
  Security and safety requirements
  Edge cases and outliers to handle
  Acceptance criteria ("done" definition)
  Testing plan
  Validation and completion evidence
  Debugging checklist
```

This is substantially richer than the simple TODO checkbox lists typical in challenge repos. Each task is a self-contained mini-engineering spec with evidence, security, testing, and debugging sections.

### 4. Relationship to Plan_atlas-pipeline-engine

The existing `Plan_atlas-pipeline-engine/` completed the framework-dev slice (assessment + 6 implementation slices, all marked COMPLETE). `Plan_atlas-production` is the **forward-looking implementation program** that begins where that assessment left off — Wave 0 (T1.1.1) verifies the active checkout and authorities against the frozen baseline commit `efa547cafc64b58d60d19dcc1e5ba32c6b046bc5`, which is the commit the pipeline-engine assessment was based on.

## Projection Validation (Deterministic Regeneration Test)

The canonical registry was fed through the included generator (`generate_todo_system.py --apply --replace-conflicts`) into a clean temporary directory, and all generated projections were compared byte-for-byte against the package originals:

| Projection | Result |
|---|---|
| `Plan-MASTER_atlas-production.md` | IDENTICAL |
| `TODO_atlas-production-registry.json` | IDENTICAL |
| `TODO_atlas-production-manifest.json` | Differs only in `"status"` field (`"passed"` vs `"not-run"`) — a validation result flag from the package's CI pipeline, not a content/structural difference |
| `TODO_atlas-production-v1.2/` | IDENTICAL |
| `TODO-MASTER_atlas-production-v2.1/` | IDENTICAL |
| 42 PART1 packs (PART1-1–42) | All 42 IDENTICAL |

**Conclusion**: All projections are deterministic and reproducible from the registry. The only difference is a status flag in the manifest that records the package-generation-time validation result.
